דף ניהול הוא דרך אחת לכתוב רשימה. לבקש מעוזר לנסח אותה, להראות את
ההבדלים ולפרסם היא דרך אחרת, וזה דורש פרוטוקול שהעוזר מדבר. לאתר יש עכשיו
שרת MCP, שנבנה בשני שלבים.

## שלב ראשון: שרת מקומי מעל ה־API

השרת הראשון רץ מקומית דרך stdio ועוטף את ה־API של האתר ב־HTTP. הוא לא
נוגע במסד הנתונים בעצמו.

- **כלים ציבוריים, תמיד**: רשימה וקריאה של רשימות, תגיות, תחומים ופעילות.
- **כלי ניהול, רק עם token**: קריאת טיוטות, שמירת טיוטה, פרסום, הסרה
  מפרסום, מחיקה ועריכת תחומים.
- **כל כתיבה היא הרצה יבשה כברירת מחדל**, ומחזירה את ההבדלים שדה אחר שדה.
  שמירה אף פעם לא משנה את מצב הרשימה, ומחיקה נדחית אם היא לא אושרה במפורש
  וההרצה היבשה לא כובתה.

ה־API של הניהול היה נגיש עד אז רק דרך ה־proxy של ההתחברות לאתר, ולכן השלב
הזה הוסיף גם API tokens, והם כבויים כברירת מחדל. כשמפעילים אותם, כל token
אקראי, נשמר רק כ־hash מסוג SHA-256, מוגבל לקריאה או לכתיבה, ותמיד פג
תוקף. token אף פעם לא יכול לנהל tokens אחרים.

כל בקשת ניהול שאינה קריאה, כולל בקשות שנדחו, נרשמת ביומן ביקורת: מי
ביקש, במה היא נגעה, ו־hash של המסמך לפני ואחרי. בדיקה מריצה כל נתיב ציבורי
מול מסד שמכיל tokens ורישומי ביקורת שמחופשים לרשימות, ומוודאת ששום דבר
מהם לא דולף.

## שלב שני: אותם כלים ב־HTTPS

השלב השני הופך חיבור של לקוח לשורה אחת, עם התחברות בדפדפן ובלי שום דבר
שרץ מקומית. הכתובת היא `https://yehudabriskman.com/mcp`.

- **OAuth 2.1, מוגש מה־API**, עם רישום לקוחות דינמי, PKCE כחובה, ו־tokens
  שקשורים לנקודת הקצה של ה־MCP כך שהם חסרי ערך בכל מקום אחר.
- **ההתחברות דרך GitHub, ורק בעל האתר עובר.** החשבון נבדק לפי שם המשתמש
  ולפי המזהה המספרי, וכל מי שאחר מקבל דף "Not authorized" ושום דבר לא
  מונפק. ה־token של GitHub אף פעם לא נשמר.
- **גישה לזמן קצר.** access token תקף לשעה. refresh token תקף לשלושים יום,
  מתחלף בכל שימוש, ושימוש חוזר באחד ישן מבטל את כל ההרשאה.
- **ההסכמה מפורשת.** הרשאת הכתיבה אף פעם לא מסומנת מראש בדף ההסכמה.
- **לכלים הציבוריים** יש נקודת קצה משלהם, בלי התחברות.

כל השרת המרוחק יושב מאחורי מתג שכבוי כברירת מחדל; כשהוא כבוי, כל נתיב
חדש עונה 404. דף בכתובת `/developers/mcp` מסביר איך להתחבר.

## למה דווקא כך

השרת הוא לקוח של אותו API שממשק הניהול משתמש בו, ולכן הוא יורש את
הוולידציה, את ה־revisions ואת בדיקות ההתנגשות של ה־API, במקום לפתח משלו.
ההרצה היבשה כברירת מחדל ויומן הביקורת קיימים כי מי שכותב הוא תוכנה:
הטעות הכי זולה לתקן היא זו שרק הוצגה, ולא בוצעה.
